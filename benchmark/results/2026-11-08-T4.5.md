# T4.5: Kernel fusion and matrix formats

Measured 2026-11-08 on the machine of `2026-11-07.md` (RX 7800 XT, Julia 1.12.6, KA 0.10.5,
AMDGPU 2.11), branch `T4.5-fusion-formats`, benchmark lock held:

```sh
julia -t 8 --project=benchmark benchmark/run.jl rocm indus continental global5m precision=double,mixed,single precond=jacobi,mc_ilu0 timed=1
```

Models, closures and columns as in `2026-11-08-T4.4.md` (steady + 30 daily steps,
`synthetic_ims(:parity)`; Δh against the `:double` Jacobi run of the same model).

## What changed

| Change | Where | Effect (global5m `:mixed`, per call) | Results |
| --- | --- | --- | --- |
| Fused formulation: boundary and storage terms, assembly and flux residual in one row kernel; the off-diagonal entries of `amat` are written only when `ibound` or `symmetric` changed (they depend on nothing else) | `formulate_system!` (csr.jl), `formulate!(::GwfModel)` | assembly 14.1 → 5.6 ms per outer iteration (fused kernel 4.4 ms + per-package record kernels 1.2 ms) | bitwise |
| Red–black MC-ILU0 setup: one work item per matrix entry for the copy (`CsrStructure.irow`), pivots through precomputed transpose positions (`ctr`) instead of scanning row m | multicolor.jl | precond setup 10.2 → 5.0 ms (+0.85 ms row factors) | bitwise |
| One host synchronisation per CG / BiCGSTAB iteration (was 2–3): the finalisation of a reduction computes alpha / omega / rho on the device (`_AlphaPost`, `_OmegaPost`, `_SetRho`), the update kernels read them; every reduction of the iteration is read after one sync | krylov.jl | CG with MC-ILU0: 3 → 1 syncs, Jacobi 2 → 1, BiCGSTAB 3 → 1 | bitwise (Jacobi, AMG) |
| `r·z` fused into the two red–black apply kernels (partials per colour, one finalisation) | multicolor.jl `_precond_apply_dot!` | −1 pass over r, z (0.48 ms) and one launch per iteration | ≤ 8e-16 relative (summation grouped by colour), same iterations |
| Static work groups (256) for all element-wise kernels | `_WG`, every `kernel(backend)` launch | no per-launch tuning; see the timer anomaly below | bitwise |
| Entry-parallel `npf_flowja!` | budget.jl | 8.3 → 2.9 ms; `calc_flows!` 17.0 → 11.7 ms per step | bitwise |
| AMG: function barrier for the untyped `fine`, smoother coefficients cached per level (no allocation per V-cycle) | amg.jl `_amg_apply!`, `_level_coefficients` | removes dynamic dispatch of every kernel launch in a cycle | bitwise |

Heads in `:double` and `:mixed` are bitwise equal to `main` for Jacobi and AMG (tiny, indus,
continental, 5 steps each, rocm); with MC-ILU0 they differ by ≤ 8e-16 relative (the fused
`r·z`), with the same outer and inner iterations everywhere (also in every row below, which
match the T4.4 iteration counts exactly).

Tried and dropped:

- **Skipping the MC-ILU0 setup when only the diagonal changes.** For red–black ILU0 every
  pivot of the second colour depends on the first colour's diagonal, so only the copy of
  the first colour's off-diagonal entries can be skipped. With the row-parallel copy this
  saved 1.3 ms of 5.0 ms; after the switch to the entry-parallel copy, checking the row
  factor per entry made the "skip" path slower (2.65 ms) than the full copy (2.15 ms), so
  it was removed. Skipping the whole setup (a stale preconditioner) would change the
  iterations and was not done.
- **SELL-C-σ** and **CSR vector**: see the SpMV section.

## SpMV formats (global5m, plain SpMV, T0.4 *min* byte model)

| Format | Float64 | Float32 |
| --- | --- | --- |
| CSR scalar (row per work item; as used) | 1553 µs, 390 GB/s (84 % of the 466 GB/s triad) | 830 µs, 475 GB/s (107 % of 445: Infinity Cache) |
| SELL-32-1 (fill 1.002) | 1438 µs, 421 GB/s (+8 %) | 797 µs, 495 GB/s (+4 %) |
| SELL-32-256 | 1444 µs | 796 µs |
| SELL-64-1 | 1431 µs, 423 GB/s | 779 µs, 507 GB/s (+7 %) |

(Scratch experiment on the assembled matrix; CSR scalar improved from T4.1's 324 GB/s with
the static work group.) Kept: **CSR scalar for every grid type.**

- SELL-C-σ gains 4–8 %, but the solver would need a second copy of the matrix in SELL
  order (+`nja·(sizeof(T) + 4)`, 0.47 GB on global5m) refreshed at every outer iteration
  (≈ one SpMV of traffic). With ~3 inner iterations per outer iteration in the daily steps
  it loses; in the steady state (~40 per outer iteration) it would save ≈ 0.1 s of 3 s.
- CSR vector (a group of lanes per row) suits long rows; with ≤ 6 off-diagonal entries per
  row lanes stay idle, and SELL (fully coalesced) bounds what better coalescing can give.
  A first kernel failed on rocm and was not pursued.
- A matrix-free 7-point stencil for DIS needs the full grid: the synthetic and real models
  are 30–40 % land after the IDOMAIN reduction (global5m 6.6 M of 18.7 M cells), so a
  stencil over all cells moves more bytes than CSR over the reduced nodes. Not done.

In-solver SpMV (`spmv_dot`, fused SpMV + dot with the scale factors), timed runs: see the
table below. The card's criterion (≥ 70 % of the triad on global5m in both precisions):
**holds**: global5m in-solver 352 GB/s `:double` (76 % of 466), 358 GB/s `:mixed` (77 %),
319 GB/s `:single` MC-ILU0 (72 % of 445) and 312 GB/s `:single` Jacobi (70 %); plain SpMV
388 / 463 GB/s (83 % / 104 %). The ≥ 85 % goal with SELL-C-σ or a stencil is not reached:
SELL-C-σ would reach ≈ 90 % for the plain SpMV but does not pay with its per-outer copy, and
the stencil does not apply (above).

## Why timed runs were faster than untimed runs (T4.1 open issue)

Not the timer. In one session, the first run of a large model after the `:tiny` warm-up
paid **≈ 0.8 s of Julia compilation** (`Base.cumulative_compile_time_ns`, measured around the
time steps only): KA 0.10 launches a kernel with a dynamic work-group size over a large range
as a `LinearLaunch` (the warm-up's small ranges are `NDLaunch`es), and the host launch code
of 13 kernels was compiled for that mode (`--trace-compile`: 13 `launch_kernel(...,
LinearLaunch{Int32}, ...)` entries, 60–125 ms each), spread over the sections of the first
steady step. The harness runs the untimed case first and the timed one second, so the
timed run got compiled code (global5m steady 4.06 s on the first run vs 2.97 s on later
runs, with or without the section hooks: `none` 2.95 s, `sync` 2.97 s, `noop` 3.11 s). On
the CPU backend (POCL) the same first-run effect applies (POCL compiles kernels at first
enqueue). With static work groups (`_WG = 256`) the launch mode no longer depends on the
size: the first run after the warm-up takes 2.95 s with no compilation. A second-run
slowdown of ~0.2 s remains when the previous `Simulation` is still being garbage collected
(finalisers freeing device memory); the harness calls `GC.gc(true)` between cases.

| indus steady < 0.35 s | 0.13 s | 0.09 s | met |
| indus < 40 µs per inner iteration | 123 µs (MC-ILU0), 77 (Jacobi) | 88 µs (MC-ILU0), 57 (Jacobi) | not met |
| assembly < 4 ms per outer iteration | 14.3 ms | 5.7 ms | not met (bandwidth: ≈ 4 ms) |
| in-solver SpMV ≥ 70 % of triad | 73 % / 69 % | 76–77 % / 70–72 % | met |
| period data < 10 ms per period | 4.3 ms | 4.3 ms | met (T4.6) |

- Assembly: the fused kernel moves ≈ 1.8 GB per outer iteration on global5m (the row's
  connections: `ja`, `jas`, `condsat`, `Δr`, `ibound` and `h` of the neighbour, ≈ 36 B per
  entry; per row ≈ 60 B), i.e. ≈ 3.9 ms at the triad bandwidth; it takes 4.4 ms plus 1.2 ms
  for the per-package record kernels. < 4 ms would need fewer bytes (e.g. `Δr` and `condsat`
  in one array, or the record formulation fused into the row kernel).
- Latency (indus): one CG iteration with MC-ILU0 is 8 kernels (direction, SpMV + dot and its
  finalisation, update and its finalisation, two apply kernels and their finalisation) and
  one synchronisation. Measured on rocm: 4.3–6.5 µs host time per launch and ≈ 18 µs from a
  launch to its completion being seen by the host, so ≈ 60–90 µs per iteration including the
  per-outer work. < 40 µs needs ≤ 4 kernels per iteration: single-pass reductions (the last
  work group finalises, with an atomic counter) and the direction fused into the SpMV
  (open).
- Daily steps: per outer iteration ≈ 11 ms of setup work (assembly 5.7, MC-ILU0 setup 5.1)
  against ≈ 3 inner iterations of ≈ 5 ms; 8.3 outer iterations per step from OUTER_DVCLOSE
  1e-9.
