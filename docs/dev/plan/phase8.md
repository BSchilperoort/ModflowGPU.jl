# Phase 8: user documentation

Task cards for this phase of [PLAN.md](../../../PLAN.md). Read PLAN.md sections 1–4 and 6 for the goals, conventions, architecture and validation rules these cards refer to.

Size: S ≈ < 1 day of agent work, M ≈ 1–3 days, L ≈ > 3 days.
`‖` marks cards that can run in parallel with their siblings.

**Why.** The documentation today is written for the agents and developers who build the
package: `PLAN.md`, the phase files, `docs/*.md` (support matrix, MF6 notes, precision,
scaling) and `CLAUDE.md`. A MODFLOW user who wants to run a model on a GPU has only the
README. This phase adds a user manual built with [Documenter.jl](https://documenter.juliadocs.org)
and published on GitHub Pages.

**Audience.** Groundwater modellers who know MODFLOW 6 (packages, input files, IMS, budgets)
and some Julia, but not KernelAbstractions or GPU programming. Second audience: model
couplers (ModflowCoupling, mGV, other BMI users). Pages explain *what to do and what to
expect*, not how the code is built; implementation detail stays in the developer notes.

**Status of the package while this phase runs.** Phase 6 is not finished (T6.2, T6.5,
T6.6, T6.7 are open). The manual describes what is supported on `main` when each page is
written. Later cards keep it current (T8.1, rule for later cards).

## Decisions (owner, 2026-11-17)

1. **Hosting:** GitHub Pages of `BSchilperoort/ModflowGPU.jl` from the `gh-pages`
   branch, pushed by the docs CI workflow (`deploydocs`). This is the only branch CI
   pushes; the local card workflow (PLAN.md section 2) is unchanged. The owner enables
   Pages in the repository settings. Until the package is tagged, only the `dev` version
   is published.
2. **Example data in the docs build:** the gallery (T8.6) downloads the pinned
   `mf6examples.zip` and the mf6 8.2 Linux binary in CI (same URLs and sha256 as
   `validation/fetch_reference.sh`, cached between runs), runs ModflowGPU and mf6 on the
   CPU, and plots both. Nothing is committed under `reference/` and no input data enters
   the repository (CLAUDE.md).
3. **Developer notes move to `docs/dev/`** (card T8.0), so `docs/` holds the manual and
   the developer material sits in one subfolder.
4. **Plotting:** CairoMakie in the docs environment only. ModflowGPU gets no plotting
   dependency or extension in this phase.
5. **Gallery build:** first try to build the whole gallery in CI. If CI cannot (time,
   memory), the gallery is prebuilt locally and its figures and tables are committed
   (T8.6 decides, from measurements).
6. **Example figures** are redrawn in Makie from ModflowGPU output, and each page links
   to the equivalent MF6 example.
7. **Exported names:** names that would clash with Base are exported under a name that
   does not clash: `run_simulation` (for `run`) and `finalize_simulation` (for
   `finalize`). Details in T8.2.

**T8.2 Public API and API reference (M) ‖**
- Depends: T8.1.
- The package exports nothing and declares nothing `public`; users write
  `ModflowGPU.run`. Decide the public surface: export the user-facing names, and
  declare the rest of the documented API `public` (Julia ≥ 1.11).
  - BMI is not affected: BMI methods are called qualified
    (`BasicModelInterface.update(model)`) and extend BMI's own functions.
  - `run` and `finalize` are separate functions from `Base.run` and `Base.finalize`, not
    methods of them, so exporting them makes `run(...)` ambiguous after
    `using ModflowGPU` (checked 2026-11-17: `UndefVarError: run not defined in Main`
    with an ambiguity hint). Adding methods to `Base.run` for strings instead would be
    type piracy. Owner decision 7: export names that do not clash, `run_simulation` and
    `finalize_simulation`. `ModflowGPU.run` and `ModflowGPU.finalize` stay as `public`
    aliases (same function objects, not deprecated) so the README, the ModflowCoupling
    patches and existing scripts keep working; the manual uses the new names.
    `initialize` and `update` do not clash with Base; check them against
    BasicModelInterface's exports and handle a clash the same way.
- Proposed groups:
  - Running: `run`, its result type, `load_simulation`, `MF6UnsupportedError`.
  - Backends and precision: `select_backend`, `backend_options`, `backend_name`,
    `supports_float64`, `resolve_precision`.
  - Stepping: `initialize`, `prepare_time_step`, `prepare_solve`, `solve`,
    `finalize_solve`, `finalize_time_step`, `do_time_step`, `update`, `finalize`,
    `get_value_ptr`, `get_value`, `set_value`, `get_var_address`, `var_addresses`,
    `input_addresses`, the time getters, `Simulation`, `StepResult`.
  - Builder: `build_dis`, `build_npf`, `build_ic`, `build_sto`, `build_oc`,
    `build_boundary`, `build_array_boundary`, `build_model`, `build_tdis`, `build_ims`,
    `write_simulation`, `SimulationSpec`.
  - Output: the `.hds`, `.cbc`, `.grb` and listing readers in `src/output/`.
  - Extension hooks (`register_backend!`, `pin_memory!`) go on a separate
    "for backend authors" page.
- Deliver: the `public` declarations; a docstring for every public name with
  signature, arguments, return value, units where relevant, and a short example
  (doctested where it runs in under a second on the CPU); API pages under
  `docs/src/api/` with one `@docs` block per group; the missing-docstring check limited
  to public names. Internal helpers stay out of the manual.
- Done when: the build has no missing-docstring warnings, every public name appears on
  exactly one API page, and the CPU tests pass (a test checks that the public names
  match the list on the API pages).

**T8.3 Installation, getting started and GPU guide (M) ‖**
- Depends: T8.1. Uses the docstrings of T8.2 where they exist (cross-references are
  added at the end if T8.2 merges later).
- `install.md`: Julia version and juliaup; adding the unregistered package by URL; one
  section per GPU vendor (AMDGPU, CUDA, oneAPI, Metal, OpenCL) with the driver or
  toolkit it needs, how to check that it works (`backend_options()`,
  `select_backend("auto")`), and whether Float64 is available; CPU-only use.
- `getting_started.md`, as a doctested walk-through on a small model built with the
  builder API and written with `write_simulation` (so no download is needed):
  1. run an existing MF6 simulation directory with `run_simulation`, and what it writes
     (`.hds`, `.cbc`, `.lst`, as asked by OC);
  2. read heads and budgets back (the readers from T8.2, and FloPy for Python users,
     since the files are MF6 binary files);
  3. the options: `backend`, `precision`, `preconditioner`, `precond_options`, with a
     "which one should I pick" table taken from `docs/dev/precision.md` and the benchmark
     results;
  4. what happens with unsupported input (`MF6UnsupportedError`, the `strict` flag), and
     with IMS options that are replaced (preconditioner, backtracking: logged warnings).
- `gpu.md`: precision presets and what they mean for accuracy; memory per million cells
  per preset (`docs/dev/scaling.md`); running on a shared GPU (next to mGV); troubleshooting
  (no Float64 on Metal or some Intel GPUs, out-of-memory, the first run being slow
  because of compilation, `allowscalar` errors).
- Done when: every code block runs in the doctests or is marked as needing a GPU, and a
  reviewer who has not used the package before can follow `install.md` and
  `getting_started.md` on a clean CPU-only environment.

**T8.4 MF6 compatibility: packages and results (M) ‖**
- Depends: T8.1.
- `compatibility/packages.md`: supported packages, blocks and options for users.
  Generate the tables at build time from the strict-loading tables in
  `src/input/supported.jl` (`SUPPORTED_OPTIONS`, `SUPPORTED_VALUES`,
  `SUPPORTED_FEATURES`, `UNSUPPORTED_PACKAGES`, `UNSUPPORTED_MODELS`), so they cannot
  drift from the code. Add by hand: the out-of-scope list and why (SFR, LAK, MAW, UZF,
  MVR, CSUB, BUY, VSC, API, GWT, GWE, PRT, PETSc), and features not yet decided (HFB,
  GNC, TVK/TVS, ATS, some output options; PLAN.md section 8 "Still open"). No card
  numbers on user pages; "planned" or "not planned" is enough.
- `compatibility/results.md`: how close the results are to mf6, and how that is checked.
  - What is compared: heads and the volumetric budget per package and per time step,
    against mf6 8.2 runs with tight closures (PLAN.md section 4).
  - Acceptance limits per preset and backend (CPU–GPU within 1e-10 relative in
    `:double`, 1e-4 m in heads in `:single`; the MF6 parity limits from section 4), and
    why `:single` and `:mixed` differ (Float32 rounding, closure floors,
    `docs/dev/precision.md`) in plain terms.
  - A parity table: one row per validated example (MF6 examples, synthetic coupling
    models, Indus) with grid size, packages, max |Δh|, max budget difference, presets and
    backends tested. A script `docs/parity/collect.jl` runs the parity comparisons
    (CPU and rocm, all presets) on the local machine and writes
    `docs/src/assets/parity.toml`, which is committed; the page renders it with the date
    and commit it came from. CI does not regenerate it (no GPU).
  - Global 5′ and Indus results from T5.3 and T5.6 in a short section (numbers only; no
    data).
  - "Check it yourself": run mf6 and ModflowGPU on the same directory and compare with
    the readers.
- `compatibility/differences.md`: behaviour that differs from mf6 on purpose, written
  for users from `docs/dev/mf6_notes.md` and the "accepted with a different behaviour" list
  of `docs/dev/support_matrix.md`: preconditioner replacement, backtracking not applied,
  Float32 closure floors, files that are not written (`DATA-SPDIS`, CSV outputs),
  listing-file differences, iteration counts that differ.
- Done when: the package tables are generated in the build, the parity table covers
  every example that passes in `test/parity/`, and every difference listed in
  `docs/dev/mf6_notes.md` that a user can observe appears on `differences.md`.

**T8.5 Stepping API and BMI guide (M) ‖**
- Depends: T8.1 (T8.2 for the cross-references).
- `coupling/stepping.md`:
  - The time-step loop, with a table from libmf6 / xmipy / modflowapi calls to the
    ModflowGPU functions, so mf6 API users can switch.
  - Addresses: the list (`var_addresses`, `input_addresses`), what each one holds,
    shape, units, and which are writable; how to find them for a model
    (`get_var_address`).
  - Host mirrors and device arrays: `get_value_ptr` (Float64, absolute heads, synced at
    call boundaries) against `get_value_ptr(...; device = true)` (precision `T`, head
    offsets, `GWF/HREF`), `get_value`/`set_value`; when each is right and what it costs.
  - A doctested example on a builder model: change the RIV stage every period from a
    Julia function, solve, read `RIV/SIMVALS`.
  - Pointers to ModflowCoupling (patched engine switch) as the production example.
- `coupling/bmi.md`: the BasicModelInterface methods, the grid functions and their
  meaning for DIS, DISV and DISU, time units, and a short BMI loop. List the BMI
  methods that are not implemented, if any.
- Done when: both pages build with their doctests, and every address in
  `var_addresses` of a model with all supported packages is documented (a test or a
  build-time check compares the two).

**T8.6 Example gallery: infrastructure and first examples (M)**
- Depends: T8.1, T8.3 (for the reading-output helpers it refers to).
- Infrastructure:
  - Example scripts in `examples/*.jl`, turned into pages with Literate.jl in `make.jl`;
    each script also runs on its own (`julia --project=docs examples/ex-gwf-toth.jl`).
  - A small docs-only helper module (`docs/ExampleTools.jl`, not part of the package)
    that downloads and verifies `mf6examples.zip` and the mf6 binary (owner decision 2),
    runs mf6 into a cache directory, and has plot helpers for head maps, cross-sections,
    hydrographs and budget bars in CairoMakie.
  - Build the gallery in CI first (CPU, `:double` and `:single`), and measure the time and
    memory on the CI runner. If CI cannot build it, add a prebuild mode
    (`docs/prebuild_gallery.jl`, run locally) that writes the figures and tables to a
    committed folder, which `make.jl` uses instead of running the examples; the page
    shows the date and commit of the prebuild. Decide per example or for the whole
    gallery, from the measurements, and record them in the card report (owner decision 5).
- Each example page has:
  1. a short description of the problem, with a link to the equivalent example in the
     MODFLOW 6 examples documentation (modflow6-examples on Read the Docs); links are
     checked by `linkcheck`;
  2. the ModflowGPU run, with the options used;
  3. the same figure(s) as the MF6 example (same quantities, layers, contour levels and
     layout), redrawn in Makie from ModflowGPU output;
  4. a comparison with the mf6 run on the same input: a difference map or plot, and a
     small table with max |Δh| and budget differences, in `:double` and `:single`;
  5. the wall time on the CPU in CI and, from the committed parity data (T8.4), on the
     GPU.
- First examples (supported and passing parity now): `ex-gwf-toth`, `ex-gwf-hanir`
  (and `-hanic` on the same page), `ex-gwf-fhb`, `ex-gwf-twri01`, `ex-gwf-lgrv-gc`.
  Plus one page with no mf6 counterpart: a synthetic coupling-type model (T3.4) at a
  small size, showing the RIV/DRN/EVT boundaries and the stepping API.
- Done when: the six pages build (in CI, or from the committed prebuild), each figure has been
  compared by eye with the original on the MF6 examples site (the reviewer records the
  check in the card report), and the comparison tables match the parity table of T8.4.

**T8.8 Performance page (S) ‖**
- Depends: T8.1.
- `performance.md`: what speed-up to expect and when the GPU helps (model size, the
  cross-over point with the CPU backend), time per time step and per outer iteration on
  the synthetic models and the global 5′ run, memory use per preset, the effect of the
  preconditioner choice, and the hardware the numbers were measured on. Source:
  `benchmark/results/`, `docs/dev/scaling.md`, the T4.7 and T5.6 reports. Figures are made

- Done when: every number on the page cites the result file it comes from, with the
  date and hardware.
